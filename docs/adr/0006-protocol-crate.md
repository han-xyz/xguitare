# The Control API's wire types are the crate `xguitare-protocol`; clients never depend on the Engine

The request and reply types of the Control API (`Request`, `Response`, `Value` and the types they carry), the constants both sides share (`SILENCE_DB`, `FRAMES_PER_PEAK`, `STILL_CLOSING`), the few pure functions both sides need (`position_frame`, `shown_file_name`, `default_socket`), the protocol version and the error codes live in `crates/xguitare-protocol`, which depends on `serde` and `serde_json` and on no workspace crate. `xguitare-core` (the Engine and the Daemon's request handling) depends on it; so do the clients, `xguitare-client` and `xguitare-gui`, which do not depend on `xguitare-core` in their normal dependencies (tests may, to feed real Daemon replies). This restores what ADR-0003 and ADR-0004 chose, a GUI that talks to the Daemon only over the Control API, from which the code had drifted: the GUI had linked the whole Engine to reach the wire types. One exception: the GUI depends on `xguitare-dsp` for the EQ curve it draws (`eq_response_db`, `MAX_FREQ_PER_RATE`), pure DSP functions with no I/O, never for a Module or the Rack.

Considered and rejected: keeping the wire types in `xguitare-core` behind a Cargo feature that switches the Engine off for clients (one crate compiled two ways across thirty modules, and a missed `cfg` shows only in one of the two builds); describing the Control API in a schema (JSON Schema or an IDL) and generating the Rust types (a generator and a second source of truth for a contract with one language on both sides); changing ADR-0004 to let the GUI link the Engine (it would match the code, but every client would compile the Engine, and a second client could reach into Engine state instead of the contract); putting the wire types in `xguitare-client` (core would then depend on a crate that does socket I/O).

What it costs. `LoopRegion`, `RenderBits`, `RenderRange` and `BankKind` are also parts of the Project file and `state.toml` formats, so the protocol crate owns types those files use, and a file-format change touches it. A config key a client reads (`socket`, `bank_kind`, `tuner_mute`) is parsed in two places, core's `Config` and the client's `ClientConfig`, kept in step by one test that feeds both the same file (`crates/xguitare/tests/client_config.rs`). A client now reads only its own keys, so a client command no longer rejects a config whose Daemon-only keys are wrong (a typo, `buffer_size = 0`, a bad `[ports]` entry); only `xguitare run` validates those. That change was accepted on purpose. `xguitare-core` re-exported the moved names from their old paths (`control::Request`, `config::BankKind`, `project::LoopRegion` and the rest, and `eq_response_db` from dsp) while the move happened in steps; those re-exports are gone, and every crate imports the names from `xguitare_protocol`.

Versioning: `status` carries `protocol_version` (`PROTOCOL_VERSION`, now 1). It goes up when a request or reply field is removed or changes meaning, never for an addition, because a client ignores an error `code` and a reply key it does not know. An error a client may act on carries a machine-readable `code` beside its `error` text (so far `still_closing`); a client treats an error without a `code` by its text, as a Daemon from before codes sends none. The protocol itself is in `docs/control-api.md`.
